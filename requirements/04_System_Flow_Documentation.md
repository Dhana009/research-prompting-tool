# Research Toolkit System Flow Documentation

## Overview

This document explains the complete flow of the Research Toolkit system, including how research queries are processed, how follow-ups work, document structure, schema, and how all components connect together.

---

## 1. High-Level Architecture Flow

### 1.1 Entry Point: MCP Server

The system starts at `mcp_server.py`, which acts as the MCP (Model Context Protocol) server interface:

1. **Tool Call Received**: User invokes a research tool (e.g., `topic_research`, `coding_research`) through Cursor IDE
2. **MCP Protocol**: Request comes via JSON-RPC 2.0 over stdio
3. **Tool Routing**: `call_tool()` function routes to the appropriate tool class
4. **Client Initialization**: Gets or creates `RouteLLMClient` (API) and `MongoDBClient` (database)

### 1.2 Research Tool Execution Flow

```
User Query → MCP Server → Tool Class → API Client → AI Model → Response
                                                              ↓
                                                         MongoDB Save
                                                              ↓
                                                         Follow-up Memory Update
```

## 2. Follow-Up System Architecture

### 2.1 Follow-Up Memory Mechanism

The system maintains an in-memory `FollowUpMemory` class that tracks the last saved document:

**Location**: `mcp_server.py` lines 42-51

```python
class FollowUpMemory:
    last_document_id: Optional[str]      # Last saved document_id
    last_conversation_id: Optional[str]   # Last saved conversation_id
```

### 2.2 How Follow-Ups Work

**Step 1: Initial Research Query**
- User asks: "What is Python?"
- System executes `topic_research` tool
- Document saved to MongoDB with:
  - `document_id`: `TR-20251127-112619-ABD31`
  - `conversation_id`: `CV-20251127-112619-ABD31`
- After save, `_update_followup_memory()` is called
- Memory stores: `last_document_id = "TR-20251127-112619-ABD31"`

**Step 2: Follow-Up Query**
- User asks follow-up: "follow up to TR-20251127-112619-ABD31, when did India get independence?"
- System checks `follow_up=True` flag
- If `parent_id` not explicitly provided, system uses `_followup_memory.last_document_id`
- New document is created with:
  - `parent_id`: `"TR-20251127-112619-ABD31"` (links to previous)
  - `conversation_id`: Same as parent (maintains conversation thread)
  - `document_id`: New unique ID

**Step 3: Automatic Linking**
- `DocumentOrchestrator._load_parent()` retrieves parent document from MongoDB
- Parent's `conversation_id` is inherited by child
- Child's `parent_id` points to parent's `document_id`

### 2.3 Follow-Up Memory Update Process

**Location**: `mcp_server.py` lines 128-153

After each successful save:
1. Query MongoDB for most recent document (sorted by `_id` descending)
2. Extract `document_id` (or `question_id` for backward compatibility)
3. Extract `conversation_id`
4. Update global `_followup_memory` instance

**Important**: Memory updates only if `save_to_db=True` (default)

## 3. Document Schema and Structure

### 3.1 Document ID Formats

**New Format (System-1)**:
- `document_id`: `{TOOL_PREFIX}-{YYYYMMDD}-{HHMMSS}-{SHORT_ID}`
  - Example: `TR-20251127-112619-ABD31`
  - Generated by: `MetadataBuilder._short_id()` (5-char UUID hex)

**Legacy Format (Backward Compatibility)**:
- `question_id`: `{TOOL_PREFIX}-{YYYYMMDD}-{HHMMSS}IST-{DAY}-{RANDOM}`
  - Example: `TR-20251126-105433IST-WED-QX18`
  - Generated by: `generate_question_id()` in `question.py`

### 3.2 Core Document Fields

**Required Fields** (from `ResearchDocument` model):
- `question`: Raw user question string
- `markdown_content`: Exact AI response (unmodified)
- `category`: Tool category enum (topic_research, coding_research, etc.)
- `question_id`: Legacy identifier (for backward compatibility)
- `timestamp_ist`: IST timestamp format: `YYYY-MM-DD HH:MM:SS IST (DAY)`
- `model_used`: AI model name (e.g., "gemini-2.5-flash")
- `complexity_score`: Integer 1-10
- `contains_code`: Boolean flag
- `estimated_segments`: Integer for future vectorization
- `language_tags`: List of detected programming languages

**System-1 Metadata Fields** (added by `MetadataBuilder`):
- `document_id`: New format unique identifier
- `conversation_id`: Links documents in same conversation thread
- `parent_id`: Points to parent document (null for root queries)
- `content_type`: "text" or "code" (auto-detected)

### 3.3 Document Assembly Process

**Location**: `document_assembler.py` lines 8-52

1. **Extract Parent Info**: If parent exists, get `parent_id` and `parent_conversation_id`
2. **Build Metadata**: Call `MetadataBuilder.build()` to generate:
   - `conversation_id`: Inherit from parent OR create new
   - `document_id`: Generate new unique ID
   - `parent_id`: Use provided parent_id or None
   - `content_type`: Detect from markdown content
3. **Assemble Document**: Combine metadata + question + markdown_content
4. **Merge Additional Fields**: Add backward-compatible fields (question_id, timestamp_ist, etc.)

## 4. Complete Execution Flow

### 4.1 Research Query Flow (Step-by-Step)

**Phase 1: Request Handling** (`mcp_server.py` lines 427-660)
1. `call_tool()` receives tool name and arguments
2. Extract `follow_up` flag and `parent_id` parameter
3. If `follow_up=True` and no explicit `parent_id`, use `_followup_memory.last_document_id`
4. Get or create API and MongoDB clients

**Phase 2: Tool Execution** (e.g., `topic_research.py` lines 35-110)
1. Determine AI model based on complexity/backup flags
2. Estimate output length and max tokens
3. Create system prompt for the tool
4. Call `get_complete_response()` to get AI response
5. Calculate complexity score (1-10)

**Phase 3: Document Creation** (`base_tool.py` lines 152-195)
1. Generate `question_id` (legacy format)
2. Generate IST timestamp
3. Detect code blocks in content
4. Detect programming languages
5. Estimate segments for vectorization
6. Create `ResearchDocument` object

**Phase 4: Document Orchestration** (`document_orchestrator.py` lines 11-66)
1. Load parent document if `parent_id` provided
2. Build full document via `DocumentAssembler.build()`
3. Save to MongoDB via `MongoWriter.save()`

**Phase 5: Memory Update** (`mcp_server.py` lines 128-153)
1. Query MongoDB for most recent document
2. Update `_followup_memory` with latest IDs
3. Return response to user

### 4.2 MongoDB Save Process

**Location**: `mongo_writer.py` lines 8-43

1. **Validation**: Check database and collection exist
2. **Duplicate Check**: Verify `document_id` doesn't already exist
3. **Insert**: Save document to MongoDB collection
4. **Return**: Document metadata (document_id, conversation_id, parent_id, etc.)

## 5. Component Connections

### 5.1 Tool Classes Hierarchy

```
BaseTool (abstract)
├── TopicResearchTool
├── CodingResearchTool
├── DebuggingTool
├── ArchitectureTool
└── GeneralPurposeTool
```

All tools inherit from `BaseTool`, which provides:
- `save_to_mongodb()`: Unified save method
- `_create_document()`: Document creation logic
- Question ID generation
- Timestamp generation
- Code detection utilities

### 5.2 Utility Classes

**DocumentOrchestrator**: Coordinates the full save pipeline
- Loads parent documents
- Calls DocumentAssembler
- Calls MongoWriter

**DocumentAssembler**: Builds final document structure
- Extracts parent information
- Calls MetadataBuilder
- Merges all fields

**MetadataBuilder**: Generates System-1 metadata
- Creates conversation_id (inherits or new)
- Creates document_id (unique)
- Detects content_type
- Sets parent_id

**MongoWriter**: Handles MongoDB operations
- Validates database/collection
- Prevents duplicates
- Inserts documents

### 5.3 Data Flow Diagram

```
User Query
    ↓
MCP Server (call_tool)
    ↓
Tool.execute() → API Client → AI Model
    ↓                              ↓
    └──────── Response ───────────┘
    ↓
BaseTool.save_to_mongodb()
    ↓
DocumentOrchestrator.save_document()
    ↓
DocumentAssembler.build()
    ↓
MetadataBuilder.build()
    ↓
MongoWriter.save()
    ↓
MongoDB Collection
    ↓
_update_followup_memory()
    ↓
FollowUpMemory (in-memory)
```

## 6. MongoDB Instance Management

### 6.1 Multi-Instance Support

**Location**: `mcp_server.py` lines 54-99

The system supports multiple MongoDB instances:
- **Primary**: Main production database
- **Secondary**: Backup or alternative database
- **Default**: Fallback instance

### 6.2 Instance Switching

**Location**: `mcp_server.py` lines 156-184

1. User calls `switch_mongodb_instance(instance_name)`
2. System closes existing connection
3. Creates new connection to specified instance
4. Updates `_active_mongodb_instance` global variable
5. All future operations use new instance

### 6.3 Instance Configuration

Instances are loaded from environment variables:
- `MONGODB_INSTANCE_{NAME}_URI`: Connection string
- `MONGODB_INSTANCE_{NAME}_DB`: Database name
- `MONGODB_INSTANCE_{NAME}_COLLECTION`: Collection name

## 7. Key Design Patterns

### 7.1 Backward Compatibility

The system maintains two ID formats:
- **New**: `document_id` (System-1 format)
- **Legacy**: `question_id` (old format)

When loading parents, system checks both:
```python
doc = collection.find_one({"document_id": parent_id})
if doc is None:
    doc = collection.find_one({"question_id": parent_id})
```

### 7.2 Conversation Threading

All documents in a conversation share the same `conversation_id`:
- Root query: Creates new `conversation_id`
- Follow-up: Inherits parent's `conversation_id`
- Enables querying all documents in a conversation thread

### 7.3 Parent-Child Relationships

Documents form a tree structure:
- Root documents: `parent_id = None`
- Follow-up documents: `parent_id = <parent_document_id>`
- Enables traversing conversation history

## 8. Error Handling and Edge Cases

### 8.1 Parent Document Not Found

If `parent_id` is provided but document doesn't exist:
- `DocumentOrchestrator._load_parent()` raises `ValueError`
- Error propagates to user
- Save operation fails gracefully

### 8.2 Duplicate Document IDs

If `document_id` already exists:
- `MongoWriter.save()` detects duplicate
- Raises `ValueError` with duplicate ID message
- Prevents accidental overwrites

### 8.3 Memory Update Failures

If memory update fails:
- Exception is silently caught
- System continues normally
- Next query may not have follow-up memory (non-critical)

## 10. Summary

The Research Toolkit uses a layered architecture:
1. **MCP Server**: Entry point and tool routing
2. **Tool Classes**: Execute research queries via AI models
3. **Document Orchestration**: Coordinates document creation and saving
4. **MongoDB Storage**: Persistent document storage
5. **Follow-Up Memory**: In-memory tracking for automatic linking

Follow-ups work by:
- Storing last document ID in memory
- Automatically linking when `follow_up=True`
- Inheriting conversation_id to maintain threads
- Supporting explicit `parent_id` for manual linking

All documents are saved with complete metadata, enabling rich querying, conversation threading, and future vectorization capabilities.
